# Security model

FrilAdd treats registry bytes, configuration, lockfiles, and existing project files as untrusted inputs. Selecting a registry delegates control of its declared source and installed content to that publisher. SHA-256 verifies bytes against a manifest. Verify the publisher and pin a reviewed commit or release for reproducibility.

The primary command is `fril`; `friladd` is a compatible alias. Both command names use the same configuration, ownership records, and transaction state, so command identity does not change the security boundary or project files.

## Paths and changes

- Files follow the Registry v1 portable ASCII relative path rules. Within a plan, the case-folded path of each file must be unique, no file can be a prefix of another target, and shared directory spelling must agree.
- Reserved target segments at any depth, ignoring ASCII case, are `.git`, `.hg`, `.svn`, `.jj`, `.friladd`, `.friladd.json`, `friladd.lock.json`, and segments beginning with `.friladd-`. These cover VCS metadata, project configuration, lock records, and staging or transaction state. Reject Windows device stems, traversal, absolute paths, alternate data streams, empty segments, and trailing dots. OS-rejected filename lengths produce operational errors.
- Use a non-symlink directory as the project root and configuration directory. Manifests and config files must be regular files. The CLI canonicalizes user-selected ancestors to support normal platform aliases. It rejects symlinks and non-directory ancestors on manifest-controlled source and destination paths beneath those roots. Use trusted local directories for the explicitly chosen registry, project, and global configuration. A local registry intentionally grants access to regular declared files under its manifest directory.
- The installer verifies source bytes before project writes and publishes each staged file using a no-overwrite operation. Existing destinations, even if they contain identical bytes, are conflicts. Dry runs perform planning and hash checks without creating project, config, lock, or cache state. A conflict can terminate planning before acquisition. Registration verifies manifest structure only. Verification reads source bytes with the installer checks and leaves consumer paths untouched.
- `installed` and `status` read only the validated lock and its owned targets. Status hashes bounded regular files after checking every path component, never follows symlinks, and does not walk or modify unrelated project paths. It makes no registry requests; explicit alias selection reads local configuration only.
- Manifests use a 1 MiB cap and configuration uses a 1 MiB cap. Registry v1 files retain the 10 MiB per-file cap. Registry v2 files are capped at 100 MiB and an operation stages at most 512 MiB total. Artifact bytes stream through a fixed 64 KiB copy buffer into private temporary files while SHA-256 and actual size are counted; declared v2 size and per-file limits are enforced during the stream, independently of `Content-Length`. Only verified staged files reach the transaction engine. Temporary staging is removed on success or failure and is not a persistent cache. Verification streams one distinct source at a time and removes its staged file. Repeated sources are acquired once; repeated declarations with contradictory digests fail. Worst-case temporary disk use is bounded by 512 MiB of acquisition scratch, plus the transaction's separate 512 MiB staged-data and 512 MiB backup limits, plus bounded lock/journal metadata.
- Catalog commands parse and validate manifests but never fetch declared artifact files. Cross-registry listing/search is limited to 64 effective configured aliases and fails as a whole when one selected manifest is unavailable or invalid. Machine output uses JSON escaping; human catalog descriptions escape terminal control characters. Registry metadata is treated as untrusted display data, and remote credentials, query strings, and fragments are not included in catalog output.
- `doctor` uses the validated lock/configuration readers, transaction pending-state inspection, and safe owned-file observations without repairing or deleting state. It makes no network request unless `--online` is set; online mode validates at most 64 configured manifests with bounded requests and does not acquire manifest-declared asset files. JSON diagnostics redact credential-bearing sources and return stable check codes instead of exposing registry locators.
- Both forms of `add` write verified files through the same journaled transaction. Copy journals can only create at unowned destinations and leave the lock bytes untouched. Managed installs commit ownership in the same transaction. Both refuse to overwrite or adopt existing unmanaged files and preserve managed files with local edits. Repeating an unchanged managed add is a no-op. Planning and dry run do not create transaction state. The transaction engine uses a project mutation lock, staged writes, backups, atomic publication and repeatable crash recovery. See [ownership and recovery](lock-and-recovery.md) for the operation bounds and filesystem guarantees. External processes can still race filesystem checks; use a local filesystem that supports hard links, atomic rename and process locking.
- FrilAdd copies source and binary bytes. It does not run provider code, package scripts or package managers. Review installed code before building or executing it.

## HTTPS

Remote registries and sources require HTTPS with TLS certificate verification and no embedded user information. A request permits up to four followed redirects and rejects the fifth redirect response. Each redirect must keep the original hostname, scheme, and effective port. V2 artifact redirects also omit queries and fragments. Artifact paths resolve against the final manifest location. Connections have a five-second connect timeout, a 30-second manifest timeout, and a five-minute artifact timeout. An explicit registry can point at a private address or use the user's configured network proxy. Same-origin policy does not establish publisher trust or isolate networks.

## Public directory status

The public directory trust design and deployment state are specified in [public-registry.md](public-registry.md). The fixed canonical endpoint is `https://registry.frillab.com/registries.json`. The operations runbook records deployment and admission evidence. The directory transport accepts only that exact HTTPS URL and has its own DNS pin for `registry.frillab.com`; it does not broaden provider origins. Provider manifests and artifacts remain restricted to HTTPS `raw.githubusercontent.com`, with credentials, suffixes, encoded or ambiguous paths rejected and repository/revision constrained to reviewed provenance. Each transport rejects any DNS answer outside global unicast ranges, disables environment proxies, pins reqwest's resolver to checked addresses, retains TLS hostname verification, rejects redirects, and bounds response size and duration. These controls do not defend against compromised approved hosts or a compromised local CA store. Listing attests to reviewed provenance and immutable manifest bytes, not code safety. Explicit custom registry operations retain their existing transport.

Community authorization is per add/update/restore invocation. A lockfile is untrusted project data and stores provenance only; it cannot grant consent. `--trust-community ID` is required for each community provider in the operation graph, including lock-based restore. A changed publisher, origin, revision or manifest digest therefore requires a fresh explicit authorization. Transitive providers are checked individually. Offline restore relies on exact locked locator, digest and size and does not consult the directory. Lock validation rejects a claimed official identity that does not match the generic FrilLab namespace/repository rule.

Compatibility allows queries in explicit and registered URLs. Keep credentials out of these URLs because configuration stores the original locator. Download errors emit only the HTTPS origin and a reason or HTTP status. `registry list` redacts the path and suffix if a configured remote URL contains user information, a query, or a fragment. Lock and JSON output omit credentials, queries, and fragments from provenance. For a redirected artifact, the lock records the final same-origin response path after removing those sensitive URL parts.
