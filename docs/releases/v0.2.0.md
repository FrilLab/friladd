# FrilAdd v0.2.0

FrilAdd v0.2.0 is the stable provider-independent distribution CLI release. FrilAssets real-asset and FrilRemotion composition integrations were not release prerequisites and remain unperformed; their status and follow-up are documented in [the qualification report](../distribution-roadmap.md) and [issue #33](https://github.com/FrilLab/friladd/issues/33). FrilAdd does not include provider-specific code or built-in provider resources.

## Highlights

- Managed, idempotent installation with ownership lock, status, safe update/remove/restore, and recoverable project transactions.
- Registry v2 metadata, portable target mapping, explicit cross-registry dependency resolution, and advisory package requirement reporting.
- Bounded large-file streaming and SHA-256 verification before transaction commit.
- Deterministic list/search/info output, versioned JSON, offline doctor diagnostics, and registry verification.
- Provider-independent CLI with Registry v1 compatibility and platform-specific npm binaries.
- Primary `fril` commands for Cargo and npm installations, with the `friladd` command kept as a backward-compatible alias.

## Install and upgrade

Install with:

```sh
npm install --global friladd@0.2.0
# or run without a global install:
npx --yes friladd@0.2.0 --help
npm exec --package=friladd -- fril --help
pnpm dlx friladd --help
```

Upgrade an existing global install with:

```sh
npm install --global friladd@0.2.0
fril --version
friladd --version
```

The npm package and Rust crate remain `friladd`; native release files keep their `friladd-<target>` names and also provide `fril-<target>` binaries. Cargo and npm expose both executable names. `fril --version` prints `fril 0.2.0`; the backward-compatible `friladd --version` continues to print `friladd 0.2.0`. Both names operate on the same project state. Use `npx friladd`; `npx fril` is not an equivalent package invocation.

The project configuration (`.friladd.json`), lockfile (`friladd.lock.json`), Registry v1 manifests, and existing command forms remain separately versioned and compatible. Before lifecycle operations on projects installed by earlier FrilAdd versions, inspect state with `fril installed` and `fril status`; v0.2.0 will not silently claim pre-existing unmanaged files.

Use `fril --help` for the command list. `friladd` remains supported and is not deprecated. See [README](../../README.md), [CLI contract](../cli-contract.md), [security model](../security-model.md), [Registry v2 contract](../registry-v2.md), and [lock/recovery contract](../lock-and-recovery.md).

## Supported packaged targets

The release workflow builds and smoke-tests npm packages containing native binaries for Linux x64 (GNU), macOS ARM64, macOS x64, and Windows x64 (MSVC). Linux ARM64 is not currently a supported packaged target.

## Known limitations

- FrilAssets did not have a released reviewed asset and registry available during qualification. GLB byte verification, license/provenance review, and a consumer render remain unperformed.
- FrilRemotion had a published FadeIn primitive, which was installed and rendered in a clean consumer; it did not publish the real composition and dependency metadata required for composition qualification. That composition test remains unperformed.
- These provider-specific results are not represented as passed integration tests and do not limit use of other providers that follow the documented registry contracts. Follow-up qualification is tracked in issue #33.
- Linux ARM64 is not a supported npm packaged target.
